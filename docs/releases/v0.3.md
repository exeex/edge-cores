# v0.3 — Flexible SRAM, native FP4 and PyTorch module compilation

v0.3 redesigns the edge-e3 SRAM scheduling mechanism to handle data formats
with different element and transfer widths. This enables higher-precision
partial sums and a shared packed weight/scale loading path. NNC also gains
reusable PyTorch modules and an explicit `import nnc` / `nnc.compile()` flow.

## Main changes

- **BF22 partial sums in FP32 storage.** Tensor partial sums increase from
  BF16 to BF22 precision: one sign bit, eight exponent bits and thirteen
  fraction bits. Intermediate results use 32-bit FP32 containers, with the
  low ten bits zero. This preserves small contributions across K tiles;
  final public Tensor outputs can still be BF16. FP32 storage does not imply
  full FP32 arithmetic precision.
- **More weight formats.** Alongside BF16 and signed INT8, the Tensor weight
  path supports packed FP4 E2M1, FP8 E4M3FN and FP8 E5M2. These are Tensor
  weight formats, in addition to the existing scalar conversion examples.
- **Native MXFP4 and NVFP4 weight Linear.** MXFP4 uses E2M1 weights with
  K32 E8M0 byte scales; NVFP4 uses K16 E4M3FN byte scales and a per-tensor
  global scale rounded to BF16. Both use dense paired-group DMA slots,
  BF22 accumulation and BF16 activations/output, with runnable public
  examples. The NVFP4 global scale does not retain full FP32 precision.
- **WSLD replaces the dedicated WLD loader implementation.** The combined
  weight/scale loader reads packed slots containing scales followed by weight
  tiles. Existing software-facing WLD and SLD intrinsics remain available.
- **Parameterized group-wise quantization.** A WSLD slot configures its weight
  type, number of 8x8 tiles, transpose mode and either one broadcast scale or
  eight output-lane scales. For output-major E3 weights, `T` tiles share a
  scale over a K group of length `8*T`. FP4 and both FP8 formats can therefore
  use different group lengths. Scale payloads support BF16, native FP16,
  E8M0 bytes (MXFP4), and E4M3FN bytes with a BF16 global scale (NVFP4).
  See NNC's [native FP4 format and numerical boundaries](../../src/edge-nnc/MICROSCALE_LINEAR.md).

## NNC PyTorch module API

NNC now provides `nn.Module` wrappers such as `LinearFp4`, `LinearMxFp4`,
`LinearNvFp4` and `LinearQ8_0` around ordinary `torch.nn.Linear` layers,
alongside the existing function-form ops. `nnc.compile(model, example_args,
out_dir=...)` exports composed models to C++ and packed weights. The
[Llama 3 example](../../example/llama/README.md) now uses reusable NNC modules
throughout its transformer-block graph and the same compile entry point.

The planned extension is user-defined quantization strategies targeting NNC's
supported ops and packing contracts. Current wrappers use preset quantizers;
constructing a quantized Linear module from user-quantized weights/scales is
not yet implemented. See the [README demo](../../README.md#pytorch-to-asic-rtl-with-nnc).

## Q8_0-style configuration

Signed INT8 weights with four tiles and eight FP16 lane scales give each
output channel one scale per 32 K elements: `w = scale * q`, with no zero
point. This provides the grouping and dequantization structure of llama.cpp
Q8_0. It uses an E3-packed layout: eight scales, followed by four 8x8 INT8
tiles (272 bytes per slot).

The tiled slot is not directly usable as a GGUF/Q8_0 row block. Upstream
[llama.cpp defines Q8_0](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-common.h)
with an FP16 scale and 32 signed INT8 values per block. E3 preserves these
scale bits and INT8 codes while repacking eight row blocks into hardware
tiles. No GGUF file importer is provided, and accumulation is not promised
to be bit-identical to llama.cpp. See the public
[Q8_0 packing and arithmetic contract](../../src/edge-nnc/QUANT_LINEAR.md).

## Runnable examples

Each named quant spec has its own PyTorch/NNC example:

| Quant spec | Source model and runner |
| --- | --- |
| FP4 E2M1 | [linear_fp4](../../example/linear_fp4/README.md) |
| MXFP4 (E2M1 / K32 / E8M0 scales) | [linear_mxfp4](../../example/linear_mxfp4/README.md) |
| NVFP4 (E2M1 / K16 / E4M3FN scales + BF16 global) | [linear_nvfp4](../../example/linear_nvfp4/README.md) |
| Q8_0-style INT8 | [linear_q8_0](../../example/linear_q8_0/README.md) |
| FP8 E4M3FN | [linear_fp8_e4m3fn](../../example/linear_fp8_e4m3fn/README.md) |
| FP8 E5M2 | [linear_fp8_e5m2](../../example/linear_fp8_e5m2/README.md) |

```sh
PYTHON=.venv/bin/python ./example/linear_fp4/run.sh
```

NNC generates each named `linear_*` C++ call and packed weight payload from
the source model. Each example's `run.sh` builds the saved headers and binary
payloads and compares the public E3 simulator result with its saved quantized
PyTorch golden; it does not regenerate them. The example READMEs document
explicit regeneration. All named entries in `linear_quant.hpp` forward to
the shared `linear_weight_slots` kernel.

The original FP4 precision, scale-change and ring-wrap models remain in
NNC's smoke suite. Low-level packing, configurable scale groups, both
transpose modes and all five hardware formats remain covered by NNC-owned
C++ regressions through `./tests/nnc/packed.sh`; see the
[packed WSLD tutorial](../tensor-packed-wsld.md).

## Software ownership

E3 product headers and the intrinsic manual are maintained in
`src/edge-e3/include/`; compiler lowering and libnn remain in `src/edge-nnc`.
The workspace exposes just `cpp/intrinsic/edge_intrinsic.hpp` and
`cpp/libnn/ops.hpp` as relative includes of the submodule umbrella headers.
The memory map and `cpp/baremetal` single-core startup/linker settings remain
workspace-owned. Startup now initializes ordinary writable literal arrays by
copying `.data` from ROM to RAM before `main()`. There are no symlinks under `cpp/`;
existing workspace include paths remain available.
NNC integrations supply the matching E3 SDK through `--e3-include`, alongside
`--edge32-include` for the instruction backend.

## Compatibility and scope

- Wide-H4 BF22 P/O vectors use eight contiguous 32-bit words and 32-byte-aligned
  bases. Rebuild code using older intermediate P/O layouts. Public BF16 tensor
  layouts remain contiguous.
- Hardware WSLD parameters are broader than compiler lowering: NNC's
  `linear_fp4` preset uses K32 groups and eight BF16 scales. The direct intrinsic
  example demonstrates the other group lengths.
- BF16-scaled FP4 support does not establish compatibility with every named
  four-bit quantization specification.
- This release's validation scope excludes E4. The
  [public validation audit](v0.3-validation.md) maps claims to public sources,
  exact commands, results and numerical limits. Private `test-e3` tests and
  n906 results are not used as release evidence. This is RTL simulation
  evidence, without a new physical timing,
  silicon performance or model-quality claim.
